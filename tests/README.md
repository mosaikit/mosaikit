# Mosaikit — Tests

Every automated test suite of the repository, where it lives and how it runs. The results of the latest
run of each suite are in [results/test-results.md](results/test-results.md), regenerated by
`cargo xtask test`, `cargo xtask ci`, `cargo xtask e2e` and `cargo xtask manual-tests` (and on its own by `cargo xtask test-report`).

## Layout of this folder

| Folder | What |
|---|---|
| `results/test-results.md` | Report of the latest run of every suite (committed with every phase) |
| `results/raw/` | Machine outputs of the suites (JUnit, libtest text, vitest and Playwright JSON); git-ignored |
| `e2e/` | End-to-end tests in the browser: `specs/NN-<area>.spec.ts` (run in order), `specs/support.ts` (shared helpers) |
| `manual/` | Automated runs of the manual checks of [docs/manual-tests.md](../docs/manual-tests.md) |
| `perf/` | Load test scripts (`run.mjs`, SQL and SQLite seeds, RLS and visibility checks), run by `cargo xtask perf` |
| `fixtures/<suite>/` | Test data, one folder per suite (`fixtures/manual` for the manual checks) |

## Suites

| Suite | Where | Runner | Run by |
|---|---|---|---|
| Rust unit tests | `#[cfg(test)]` modules in `crates/*/src`, `xtask/src` | cargo-nextest (or `cargo test`) | `cargo xtask test` (PostgreSQL pass) |
| Kernel integration tests | `crates/kernel/tests/*.rs` | cargo-nextest | `cargo xtask test`: on PostgreSQL and again on SQLite |
| Server HTTP tests | `crates/server/tests/*.rs` | cargo-nextest | `cargo xtask test`: on PostgreSQL and on SQLite |
| Database tests (RLS) | `crates/db/tests/*.rs` | cargo-nextest | `cargo xtask test`: on PostgreSQL and on SQLite |
| Rust doc tests | doc comments | `cargo test --doc` | `cargo xtask test` |
| Plugin tests | `../mosaikit-plugins/*/src` | `cargo test` in that workspace | `cargo xtask test` |
| Distribution tests | the folders listed in `[tests] cargo` of `distribution.toml` | `cargo test` | `cargo xtask test --dist <folder>` |
| Host UI tests | `ui/host/src/**/*.test.ts` | vitest | `cargo xtask test` |
| Plugin API tests | `ui/plugin-api/src/**/*.test.ts` | vitest | `cargo xtask test` |
| Plugin UI tests | `../mosaikit-plugins/*/ui/**/*.test.ts` | vitest | `cargo xtask test` |
| End-to-end tests | `tests/e2e/specs/*.spec.ts` (with axe); `wildcard.spec.ts` (one origin per plugin) runs on a second installation after the suite, as the suite `e2e-wildcard` of the report; `18-developer-profile.spec.ts` starts a server of its own in the developer profile (`E2E_SERVER_BIN`, set by `cargo xtask e2e`) | Playwright | `cargo xtask e2e` (`--wildcard`: only the wildcard scenario, report untouched) |
| Manual checks, automated | `tests/manual` (one test per id of `docs/manual-tests.md`, fixtures in `tests/fixtures/manual`) | Playwright | `cargo xtask manual-tests` (`--area R1-L` or `-g P3-` for the checks whose id starts so; `-- --grep P3-12` for one; `--check` compares the ids; `ci` runs the check) |
| Load test | `tests/perf/` | `cargo xtask perf` | by hand, results in [docs/reports/performance.md](../docs/reports/performance.md) |

**How many tests, and how many of them are security tests.** `python tests/count-tests.py` counts the Rust tests of the platform
(`cargo nextest list`), the security ones among them by a stated rule (`--names` lists them), the documented checks of
[docs/manual-tests.md](../docs/manual-tests.md) and the operations measured by the load test. The interface, plugin and browser tests
are counted by the report of the latest run (`results/test-results.md`). The figures on the site come from these two sources.

The layout contract (`specs/15-layout-contract.spec.ts`, rules R-1 to R-9 of [docs/refactoring-ui.md](../docs/refactoring-ui.md) section 12) walks every route of the app (derived from the navigation: sidebar, section lists, the pages of the apps) as the Administrator, a Tenant Manager and a User, at 1440x900, 1280x600 and 390x844. One walk measures the routes and writes `tests/e2e/test-results/layout-contract.json`; then one test per rule and family of routes judges the measures, so a failure names the rule, the route and the size. Run it before delivering a change to the shell, headers, lists or navigation: `cargo xtask e2e -- specs/15-layout-contract.spec.ts`. The sidebar rule (R-8) is measured on a page of every family at 1280x300. R-10 (an empty page or app shows the illustrated empty state, centred, with the primary action; checked on a fresh tenant), R-11 (every table has a fixed header row, its own scrollbar under it, a filter, sortable titles, progressive loading; exemptions in `TABLE_EXEMPT`) and R-12 (no row painted over or above the header row) judge the tables. Rules still broken by unfinished work are in `PENDING` (top of the spec, empty now) and run as `test.fixme`; remove the row when the work has merged.

The browser suite runs in groups: `tests/e2e/shards.json` lists them (the spec `01` creates the admin and the first tenants and runs first in every group; a spec in no group never runs in CI, a unit test checks it). In CI every group is a job with an installation of its own; a pull request that cannot reach the server or the shell (documentation, tools, manual checks) skips them, and a pull request or the merge queue runs the short group `smoke` only (about 10 minutes with the backend); the whole suite runs on main after every merge, and on a pull request with the label `full-e2e`. A red main is fixed before anything else is merged. The specs of a group must not need the data of a spec of another group: a spec that makes data for others (02 to 06 build the tenants and people that 07 to 14 use: they open groups b and c; 15 to 19 need only the setup) is listed first in every group that needs it.

Run a part of the end-to-end suite: `cargo xtask e2e -- specs/<file>.spec.ts -g "part of a test title"` (everything
after `--` goes to Playwright; a partial run does not replace the e2e results of the report). Heavy runs queue on
machine-wide slots and each worktree has its own port and database: see "Working in parallel" in the
[README](../README.md#working-in-parallel-worktrees-ports-heavy-run-slots).

Unit tests stay next to the code they test; this folder holds the system-level suites and the results.

### End-to-end suite: order and isolation

The e2e specs share ONE installation (a new database, plugins and server per run) and build on each other: the files run in the order of their numbers, in one worker (`workers: 1`). Parallel workers on the same installation are not safe: the Administrator has one second factor whose code the server accepts once per 30-second step, and several tests change platform-wide settings (languages, maintenance, quotas, layouts, names of tenants). A file that fails can leave state the next ones need, so read the first failure first. Parallelism is across installations instead: every checkout (worktree) has its own database and ports, and heavy runs queue on slots. The second factor is kept in `tests/e2e/test-results/admin-state.json` (emptied by the global setup at every run).
## When to run what

- While working: only the area you touch, e.g. `cargo xtask manual-tests --area R1-L` (ids that start with the prefix) or `cargo xtask e2e -- -g "<title>"`; never the whole manual suite.
- Before a merge: `cargo xtask e2e --shards` (the browser suite in the groups of `tests/e2e/shards.json`, several installations side by side, `-j N` at once, default 3; about a third of the time of the normal run) and the wildcard scenario, together with `cargo xtask ci`. The normal `cargo xtask e2e` (12-20 minutes, one installation, the report of the whole suite) is for the release. `cargo xtask e2e --shard <name>` runs one group, as a CI job does.
- The full manual suite (`cargo xtask manual-tests`, about one hour): only on an explicit release request; it is not part of `cargo xtask ci`, `test` or `e2e`. The last full run was not completed: the run of 2026-10-27 ended with 263 passed, 24 failed (findings M1-M3 in docs/reports/qa-walkthrough.md), 10 skipped on the first 296 ids; the 49 ids added later (PERF, QA, DEV, HOST: `tests/manual/checks/pending.ts`) were never executed, and the suite was not run again after upstream began requiring an email for local accounts (the seed has it now; checks that create people by hand may need one).
- Heavy runs (`test`, `ci`, `e2e`, `manual-tests`) take a machine-wide slot (`xtask/src/heavy.rs`, `MOSAIKIT_HEAVY_SLOTS`), so runs of several checkouts wait for each other instead of colliding. The manual suite shares the `e2e` slots.
