# Data

Where a plugin keeps its data, and the rules the platform applies to it. Architecture §7 has the full text.

## Two backends, one set of rules

| | PostgreSQL ≥ 15 | SQLite |
|---|---|---|
| Used by | server and Docker | the desktop version and `mosaikit-plugin dev` |
| Tables of your plugin | schema `plg_<id>` | tables `plg_<id>__<name>` |
| Protection | roles and row level security in the database | the same rules enforced by the data layer |
| `plugin.call`, `[requires] database = "postgres"` | yes | no |

Write SQL for PostgreSQL. On SQLite it is **translated** (names, casts, `now()`, intervals, `= ANY(...)`, `ILIKE`,
`json_build_object`, `string_agg`, `EXTRACT`, common `to_char` and `date_trunc`, placeholders `$n`); a construct with no
safe equivalent is refused with a clear message (`json_agg` of whole rows, `DISTINCT ON`, regular expressions,
`ALTER COLUMN TYPE`). `validate --strict` runs your migrations through that translation, so you learn it before the
desktop does. A plugin that needs PostgreSQL features says `[requires] database = "postgres"`; it then does not install on
SQLite. Check against the real database with the Docker kit.

## Tables

The tables of `[[resources]]` are generated by the host from the manifest. Further tables or views come from
migrations. **Every table** of a plugin must have:

```sql
resource_id uuid not null,   -- the kernel resource the row belongs to
tenant_id   uuid not null    -- default core.ctx_tenant() in the generated tables
```

After the migrations the host adds the foreign key to `core.resources` with `on delete cascade`, turns on RLS and
creates the policies. If a table lacks a column, the installation is rolled back.

## Migrations

Files `migrations/NNN_name.sql`, applied in order at installation and update, **in the same transaction**: if a
statement fails, everything rolls back.

- Numbered from `001`, no gap, no duplicate; the name after the number is lower case, digits and `_`.
- **A migration that was applied is never edited**: its checksum is kept, and a change is refused
  (`migration <name> differs from the one already applied`). Put the change in a new migration. In development the
  Developer tools offer to delete the plugin data and start from the first migration.
- Migrations only add: `validate --strict` refuses `drop table`, `drop column` and `truncate`, because there is no down
  script.
- Allowed by the guard: `CREATE TABLE/INDEX/VIEW`, `ALTER TABLE`, `DROP TABLE/INDEX/VIEW` (the conformance suite refuses the irreversible ones), `INSERT/UPDATE/DELETE`, `COMMENT`.
  Refused: functions, triggers, policies, `GRANT`, `SET`/`RESET`, `DO`, `COPY`, and any reference to another schema.
- They run with the role of the plugin (`SET LOCAL ROLE`), so they cannot touch `core` or other plugins. Views that use
  objects outside the schema of the plugin are refused.
- KPI views are named `kpi_*`, carry `tenant_id` and are declared in `[[kpi]]`; the declared view must exist after the
  migrations or the installation fails (`the KPI view <name> declared in the manifest does not exist`).
- Required PostgreSQL extensions (`[requires] extensions`) must be installed in the database; their schema is added to
  the `search_path` of the role after the plugin's own.
- Adding a field to a resource adds the column on update; an existing field cannot change type.

```sql
-- migrations/001_kpi.sql
create view kpi_notes_by_tag as
  select tenant_id, coalesce(tag, '(none)') as tag, count(*) as notes
  from notes group by tenant_id, coalesce(tag, '(none)');
```

## The security context

Every operation on the data of a plugin runs in a transaction on a connection authenticated as **the role of the
plugin** (`<prefix>_p_<id>`: only DML on its own schema, no access to `core` except through functions):

1. the host runs `core.set_ctx(secret, user, tenant, plugin, link)`, a `SECURITY DEFINER` function that checks a secret
   the plugin cannot read and stores the context for the current transaction;
2. it runs the statements (generic CRUD, commands, hooks);
3. commit, or rollback if anything fails.

The plugin cannot forge the context (it does not know the secret) nor leave its role. On SQLite the context lives on the
Rust side of the connection and SQL cannot change it.

## Row level security

For every table the host creates policies, so a query returns and changes only what the caller may:

| Policy | Rule |
|---|---|
| read | the row's resource is visible to the caller at level 1 or more (membership, ownership, inherited grants, public link) |
| insert | `core.can_access(resource_id, 2)` and `tenant_id` is the tenant of the context |
| update | write level (2) |
| delete | manage level (3) |

You write `select * from notes` and get the caller's rows. A tenant manager sees metadata, never content; and the plugin
cannot opt out. Inside your SQL you may read `core.visible_resources` (the metadata of the visible items of this plugin)
and call `core.can_access(id, level)`, `core.level_of(id)`, `core.ctx_user()` and `core.ctx_tenant()`.

Lists of the CRUD are paged by key (`limit` default 50, at most 500; the cursor is the key of the last row), and `sort`
is an allow-list of declared fields.

## What the SQL guard allows at runtime

The queries of the logic (`ctx.db().query/exec`) go through the guard, a **second** defence after the role and RLS:

- only `SELECT`, `INSERT`, `UPDATE`, `DELETE` (and `WITH`);
- one statement per call;
- no `SET`, no system functions (`pg_*`, `set_config`, `current_setting`, `dblink`, `lo_*`, XML export functions…), no other
  schema except `core.visible_resources` and the functions `can_access`, `level_of`, `ctx_user`, `ctx_tenant`;
- statements run as prepared statements with a 15 s timeout on PostgreSQL.

The guard returns the SQL serialized again from its parse: what was analysed is what runs. A rejected statement is the
error `invalid SQL: …`, `statement not allowed in plugins: …`, `object not accessible to plugins: …` or
`function not allowed in plugins: …`.

## Never from a plugin

Read another plugin's tables or `core`; create roles, policies or triggers; change the ownership of an object. To use
another plugin's data, call its commands (`calls`): it applies its own rules for the same user.
