Today a Java extension may use only `kernel-api`, the Jakarta APIs and the Quarkus extensions of the
kernel: its JAR holds its own classes and nothing else (ADR-0004). A common extension such as a
catalog needs libraries the kernel does not have (a database driver, a reader of a file format), and
products compose several such extensions (ADR-0041).

## Analysis

The kernel loads a Java extension by copying its single JAR into `providers/` and running the
Quarkus augmentation again at the next start: the entities, beans and REST resources of the
extension become part of one application, built once, on one class loader. Two ways let an
extension bring libraries.

- **Libraries added to the class path of the kernel at augmentation (chosen).** The package carries
  the libraries in `lib/`, the launcher copies them into `providers/` as it does with the JAR of the
  extension, and augmentation adds them as application archives. It costs a copy and a check:
  nothing in the start of the kernel changes, the rollback of ADR-0004 covers a library that breaks
  the build, and the contracts between extensions (MK-134) stay plain Java types shared by everyone.
  The price is that every library exists once in the installation: two versions of the same library
  cannot coexist, so a conflict is refused at installation with a clear message, and the developer
  aligns the version, uses the one of the kernel, or relocates (shades) the library into a package
  of its own.
- **An isolated class loader per extension (deferred).** It would let two extensions use two
  versions of one library, but Quarkus processes CDI beans, JPA entities and REST resources at build
  time, in one closed application: code loaded later by a class loader of its own takes no part in
  augmentation, so the extension would lose the injection of the beans of the kernel, its entities
  and its REST resources, which are the reason a Java extension exists. Types shared across loaders
  (the contracts of MK-134, the records of `kernel-api`) would need parent-first loading for those
  and child-first for the rest: the machinery that ADR-0004 decided against ("No custom class
  loaders or OSGi"), with its leaks and its extra memory. It can be reconsidered for libraries
  without beans or entities, used behind a facade, if conflicts turn out to be frequent.

A library is identified by its Maven `groupId:artifactId`, and versions compare exactly. The list of
what the kernel provides is produced from its dependency tree at build time, shipped with the
installation for the check, and published in the guide; the parent POM imports it as a BOM, so that
the transitive dependencies already in the kernel resolve to `provided`.
