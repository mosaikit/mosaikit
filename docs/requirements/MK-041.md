---
id: MK-041
title: S3-compatible file storage and file service for extensions
area: kernel
priority: P1
status: done
depends: [MK-019, MK-032]
acceptance:
  - An extension stores and reads a file through the service without knowing the credentials of the
    store.
  - A person cannot read a file of another organization, or of a team they do not belong to, even
    with its identifier.
---

The kernel keeps files in an S3-compatible object store, one prefix per organization, and offers
extensions a file service that applies the rights of the person and records the audit. The portable
distribution brings MinIO or uses a directory. See ADR-0029.

## History

- 2026-10-13: in progress — S3-compatible storage behind a kernel file service for extensions.
- 2026-10-13: the kernel keeps files in a directory or an S3-compatible bucket (`mosaikit.files.*`),
  under `<organization>/<extension>/<id>`, with their metadata in `mk_kernel.stored_file` under
  row-level security (migration V24), and serves them through `/api/v1/files/{extension}` with
  ranges and cache validators; a person reads only the files of their organization and of their
  teams (acceptance 2 through the REST API). Acceptance 1 waits for the Java API of extensions.
- 2026-10-13: done — Java extensions use the file service through `FileStorage` in `kernel-api`
  (the kernel bean `ExtensionFiles`), which applies the same checks as the REST API; acceptance 1
  and 2 are covered through it (`FileStorageApiTest`) and through the REST API (`FileStorageTest`).
- 2026-10-13: files linked to a resource follow its sharing (MK-055): any level reads and lists them,
  a level that edits attaches, replaces and deletes them, in the REST API, the `FileStorage` bean and
  the row-level security (migration V29); files without a resource keep the rules of the organization
  and its teams (`FilesFollowSharingTest`).
