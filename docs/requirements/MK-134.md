---
id: MK-134
title: Versioned contracts between extensions, on the server and in the frontend
area: extensions
priority: P1
status: planned
depends: [MK-020, MK-131, MK-132, MK-133]
decisions: [ADR-0019, ADR-0041]
acceptance:
  - An extension publishes a backend contract as Java interfaces in a small API artifact of its own;
    other extensions implement it, and the extension that owns the contract finds the
    implementations through CDI, only those of extensions active in the organization of the request.
  - A catalog finds the connectors installed for an organization through such a contract; a
    connector installed, or turned off, is found, or no longer found, without changes to the catalog.
  - A frontend extension point declares the type of the payload of its contributions as a JSON
    Schema; contributions that do not match it are refused at installation with the reason, and
    `@mosaikit/sdk` gives the owner of the point the typed contributions.
  - Contracts are versioned. The API artifact follows semantic versions and an extension point
    carries a major version; implementations and contributions declare the version they target, and
    a breaking change publishes a new version next to the old one, both served until the old one is
    retired.
  - The API artifact is loaded once even when several extensions bring it (MK-131); compatible
    versions of it resolve to the highest one.
---

Extension points (ADR-0019) let an extension contribute elements to the frontend of another, but
their attributes are untyped, and on the server extensions may talk only through events. A catalog
that lists data from several sources needs a call contract on the server ("list the items of this
connection", "read this item") with the implementations of the connectors installed; a dashboard
needs typed widget contributions. The contract belongs to the extension that defines it, not to the
kernel.
