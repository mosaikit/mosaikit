id: MK-123
title: Read-only views of people, organizations, memberships and teams for external services
area: security
priority: P1
status: done
depends: [MK-032, MK-056]
acceptance:
  - A database login created for an external service reads the published views of accounts,
    organizations, memberships, teams and their members, and nothing else of the kernel.
  - A change of team made through the API shows in the views at once.
  - The views keep their names and columns across releases; a change is announced as a breaking
    change of the platform.
---

Services that apply the decisions of the platform by themselves, such as a map server that reads the
roles of a person from a database, need to know who belongs to which organization and team. Today the
only way is to read the internal tables of the kernel, which may change in any release. The kernel
publishes read-only views with stable names and columns, for a dedicated database login, so that such
services read a contract and not the internals.

## History

- 2026-10-13: written after the proofs of a product built on Mosaikit, where a map server read the
  roles of people through views over internal tables of the kernel.
- 2026-10-13: in progress — published read-only views and a database login for external services.
- 2026-10-13: done. Views `account`, `organization`, `membership`, `team` and `team_member` in schema
  `mk_published` (migration V21), readable by the role `mk_<database>_reader` that the kernel creates
  at start, and optionally by a login from `mosaikit.database.published-views.*`;
  `PublishedViewsTest` proves what the login reads and cannot, that a change of team through the API
  shows at once, and pins the columns. Contract in docs/development/published-views.md.
- 2026-10-14: the Java code of extensions reads the same people and teams through the `People`
  bean of kernel-api, without a database login (#105).
